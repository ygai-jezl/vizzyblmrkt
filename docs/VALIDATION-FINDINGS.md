## Firestore to BigQuery real-time analytics pipeline

**Summary:** The PRD core mechanism is broadly sound: the Stream Firestore to BigQuery Firebase Extension (firestore-bigquery-export) is still documented and recommended by Firebase and Google in 2026 for sending real-time incremental updates from a Firestore collection to BigQuery, writing an append-only changelog of CREATE, UPDATE, DELETE, and IMPORT events plus a latest-state view. However several specific PRD claims are wrong or risky. The biggest factual error is the cost and tier claim: the BigQuery sandbox explicitly does NOT support streaming inserts, DML, or the Data Transfer Service, and Firebase Extensions require the paid Blaze plan because they run on Cloud Functions, so the pipeline cannot run on free tier or sandbox and mandates a billing account. The sub-5-second near-real-time SLA is partially incorrect: streamed rows are queryable immediately after BigQuery acknowledges the write, but the end-to-end path from Firestore through an Eventarc trigger to a Cloud Function to BigQuery carries no Google SLA, Eventarc delivers at-least-once with no ordering guarantee, and partition placement and copy availability can lag minutes (rarely up to 90). Datastream for Firestore does not exist; Datastream only sources MySQL, PostgreSQL, AlloyDB, SQL Server, and Oracle. For a latest-state table with accurate deletes, the modern approach is BigQuery change data capture via the Storage Write API. Nested fields such as the answers map and UTM params land in a JSON data column queried with JSON_VALUE and JSON_QUERY or exposed via schema views.

### Validated PRD claims

- **[CONFIRMED]** The Firestore-to-BigQuery Extension forwards document updates and is the recommended path.
  - Reality: Firebase official Integrate with BigQuery guide (current in the 2026 corpus) still recommends the firestore-bigquery-export extension to send real-time, incremental updates from a Firestore collection to BigQuery. Security comes from the service account and BigQuery IAM, not from the extension acting as a network secure forwarder.
  - Cites: https://firebase.google.com/docs/firestore/solutions/bigquery, https://docs.cloud.google.com/firestore/native/docs/solutions/bigquery
- **[PARTIALLY-CORRECT]** The extension mirrors create/update/delete events as an append-only event log with operation type CREATE/UPDATE/DELETE/IMPORT plus a latest-state view.
  - Reality: The extension is built on Firestore 2nd-gen Cloud Functions triggers (onDocumentCreated, onDocumentUpdated, onDocumentDeleted, onDocumentWritten) and writes a raw append-only changelog table plus a derived latest view; IMPORT is used for backfill. The corpus confirms the trigger model and real-time nature but does NOT contain the extensions.dev README enumerating exact changelog columns (timestamp, event_id, document_name, document_id, operation, data, old_data); verify that column list against the README. A no-op write where data is unchanged does NOT generate an event.
  - Cites: https://firebase.google.com/docs/firestore/solutions/bigquery, https://firebase.google.com/docs/firestore/extend-with-functions-2nd-gen, https://docs.cloud.google.com/firestore/native/docs/eventarc
- **[INCORRECT]** The pipeline provides a sub-5-second near-real-time streaming SLA.
  - Reality: There is no documented end-to-end sub-5-second SLA. BigQuery makes streamed rows available immediately for query (Storage Write API default and committed streams, and legacy insertAll), so the BigQuery leg is sub-second to seconds. But Firestore triggers for Eventarc are delivered at least once with ordering not guaranteed, so duplicates and out-of-order rows are expected and cold starts and retries add latency. Ingestion-time partition placement has no SLA (typically minutes, rarely up to 90) and recent rows can be unavailable for copy or read for minutes. Near-real-time within seconds is fair; a hard sub-5-second SLA is not supportable.
  - Cites: https://docs.cloud.google.com/bigquery/docs/write-api, https://docs.cloud.google.com/bigquery/docs/write-api-streaming, https://docs.cloud.google.com/firestore/native/docs/eventarc, https://docs.cloud.google.com/bigquery/docs/streaming-data-into-bigquery
- **[INCORRECT]** BigQuery 1TB free query per month with sandbox/free tier is used for analytics on this streaming pipeline.
  - Reality: The free tier and sandbox give 1 TiB on-demand queries per month and 10 GiB active storage per month, but the BigQuery sandbox does not support Streaming data, DML, or the Data Transfer Service. The extension streams, so it cannot run against a sandbox. Firebase Extensions also require the Blaze plan because they run on Cloud Functions. The pipeline mandates a Blaze billing account and a billing-enabled, non-sandbox BigQuery project; free allowances still apply on Blaze but sandbox is the wrong word and the implied zero-dollar path is not real.
  - Cites: https://docs.cloud.google.com/bigquery/docs/sandbox, https://firebase.google.com/docs/projects/billing/firebase-pricing-plans, https://firebase.google.com/docs/functions/faq-and-troubleshooting, https://cloud.google.com/bigquery
- **[CONFIRMED]** BigQuery streaming insert / Storage Write API is the cost model to budget for.
  - Reality: Legacy streaming inserts (tabledata.insertAll) cost 0.01 USD per 200 MiB with a 1 KB minimum per row and no free allowance. The Storage Write API, recommended for new projects with lower cost and an exactly-once option, costs 0.025 USD per 1 GiB with the first 2 TiB per month free. Query on-demand is 6.25 USD per TiB scanned with the first 1 TiB per month free. Storage gives the first 10 GiB per month free at about 0.02 USD per GiB physical, and data untouched for 90 days drops about 50 percent. For a low-volume waitlist, ingestion and storage stay within free allowances; query scanning is the main variable cost.
  - Cites: https://cloud.google.com/bigquery, https://docs.cloud.google.com/bigquery/docs/write-api, https://docs.cloud.google.com/bigquery/docs/streaming-data-into-bigquery, https://docs.cloud.google.com/bigquery/docs/best-practices-costs
- **[INCORRECT]** Datastream for Firestore to BigQuery is a viable alternative.
  - Reality: Datastream does NOT support Firestore as a source; it only reads change events from MySQL, PostgreSQL, AlloyDB, SQL Server, and Oracle. Real alternatives are the firestore-bigquery-export extension (default), a Pub/Sub BigQuery subscription with BigQuery CDC, application-level dual-writes via the Storage Write API, and the managed Firestore export to BigQuery load which is batch only, not real-time, needs a collection-ids filter, and cannot append to an existing table.
  - Cites: https://cloud.google.com/datastream-for-bigquery, https://docs.cloud.google.com/pubsub/docs/bigquery, https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-firestore
- **[CONFIRMED]** Deletes are represented for historical analytics accuracy.
  - Reality: The extension append-only changelog records a DELETE operation row preserving full history while the latest view reflects deletion. Separately, BigQuery CDC via the Storage Write API uses the _CHANGE_TYPE pseudocolumn (UPSERT or DELETE) to maintain a latest table; DELETE removes by primary key, with optional _CHANGE_SEQUENCE_NUMBER for ordering. CDC keeps a 2-day delete-retention window, requires primary keys, and CDC tables cannot use mutating DML, wildcard-table queries, or search indexes. For historical accuracy prefer the append-only changelog.
  - Cites: https://docs.cloud.google.com/bigquery/docs/change-data-capture, https://docs.cloud.google.com/pubsub/docs/bigquery, https://firebase.google.com/docs/firestore/extend-with-functions-2nd-gen
- **[CONFIRMED]** Nested/custom fields (answers map, UTM params) go in the extension JSON data column; use wildcard/schema views.
  - Reality: The extension stores the full document in a single data column as JSON. BigQuery natively supports JSON with schema-on-read, a 500 nesting limit, no partitioning or clustering on JSON, and row-level security cannot apply to JSON. Query with JSON_VALUE, JSON_QUERY, JSON_QUERY_ARRAY, and typed or LAX extractors. The extension ships a schema-view generator (fs-bq-schema-views) to project JSON paths into typed columns. The batch Firestore export path treats map fields as bytes past 10,000 unique field names, making sub-fields unqueryable, so prefer the JSON-column extension path.
  - Cites: https://docs.cloud.google.com/bigquery/docs/json-data, https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-storage-json, https://docs.cloud.google.com/bigquery/docs/loading-data-cloud-firestore

### Recommendations

- [P0] **Fix the cost narrative: requires Blaze plus billing-enabled BigQuery, not free tier or sandbox** — Drop the sandbox and free-tier framing. The sandbox blocks streaming, DML, and the Data Transfer Service; extensions require Blaze (Cloud Functions). Keep messaging that you stay within free allowances (1 TiB query per month, 10 GiB storage per month, 2 TiB per month Storage Write API) but a Cloud Billing account is mandatory. Set budget alerts and a billing-cap function since alerts do not cap spend.
- [P0] **Restate latency as a target, not an SLA; design for at-least-once and out-of-order delivery** — Replace the sub-5-second SLA with typically a few seconds, best-effort, no SLA. Firestore Eventarc triggers are at-least-once with no ordering, so de-duplicate in the latest view (window by document_id ordered by Firestore update timestamp) or use BigQuery CDC with _CHANGE_SEQUENCE_NUMBER, and make downstream analytics idempotent.
- [P1] **Remove Datastream for Firestore; list the real alternatives** — Datastream sources only MySQL, PostgreSQL, AlloyDB, SQL Server, and Oracle. Legitimate options are the extension (default), a Pub/Sub BigQuery subscription with CDC, and app-level dual-writes via the Storage Write API, which fits the PRD avoid-firebase-admin and scoped-service-account posture better.
- [P1] **Use the Storage Write API default stream and BigQuery CDC, not legacy insertAll** — The Storage Write API default stream is cheaper (0.025 USD per GiB with 2 TiB per month free versus 0.01 USD per 200 MiB with no free tier), available immediately for query, with exactly-once via committed streams. For a latest table with correct deletes use CDC (_CHANGE_TYPE UPSERT or DELETE, _CHANGE_SEQUENCE_NUMBER), primary key tenantId plus document_id. CDC tables cannot use mutating DML, wildcard tables, or search indexes.
- [P1] **Partition by date and cluster by tenantId for cost and tenant isolation** — Partition the changelog by ingestion DATE and cluster by tenantId to bound scan cost (6.25 USD per TiB after the first free TiB) and make Authorized Views and RLS by tenantId cheap, supporting the multi-tenancy isolation requirement. Avoid scanning raw JSON across all partitions in dashboards.
- [P2] **Model survey answers and UTM params as JSON with schema views** — Keep the answers map and UTM params in the JSON data column and project reported fields (utm_source, utm_campaign, answers.qN) into typed columns via fs-bq-schema-views or views using JSON_VALUE and JSON_QUERY. This avoids the 10,000-field-name limit that breaks the batch export path and keeps dashboards fast.
- [P2] **Prefer the append-only changelog for historical accuracy; plan the backfill** — Query the append-only changelog (full event history with DELETE rows) rather than only the latest view for historicals and churn. To rebuild, re-run the import or backfill from Firestore (fs-bq-import-collection); plan and document an initial backfill.

### Cost notes

- BigQuery query on-demand is 6.25 USD per TiB scanned with the first 1 TiB per month free; partition by date and cluster by tenantId and query the latest view to keep scans small.
- Storage Write API ingestion is 0.025 USD per 1 GiB with the first 2 TiB per month free, effectively free at waitlist volumes; it is the recommended ingestion path.
- Legacy streaming inserts (tabledata.insertAll) cost 0.01 USD per 200 MiB with a 1 KB-per-row minimum and NO free allowance; avoid for new builds.
- BigQuery storage gives the first 10 GiB per month free at about 0.02 USD per GiB physical or 0.01 to 0.02 USD per GiB logical; tables untouched 90 days drop about 50 percent to long-term pricing.
- Firebase Extensions require Blaze; each installed extension costs roughly 0.01 USD per month baseline Cloud Functions resources even if idle, plus per-invocation cost for every Firestore change event.
- Firestore export/import as a batch alternative is billed at 1 read per document exported plus Cloud Storage storage; it is not real-time and cannot append to an existing BigQuery table.
- BigQuery CDC delete-retention keeps DELETE operations for a 2-day window at standard storage pricing; CDC apply consumes compute on-demand or via a BACKGROUND reservation which the Standard edition lacks.

### Security notes

- Tenant isolation in BigQuery: use Row-Level Security or Authorized Views keyed on a tenantId column; RLS cannot be applied to JSON columns, so promote tenantId to a top-level typed STRING column, not just inside the JSON data blob.
- The Pub/Sub BigQuery subscription path needs roles/bigquery.dataEditor on the Pub/Sub service agent or a user-managed service account; use a per-tenant-scoped user-managed service account for least privilege.
- The extension runs as a Cloud Function with a BigQuery-writing service account; scope that account to one dataset and tenant-partitioned tables and keep it outside the public landing-page trust boundary.
- Cloud Functions reads and writes are not governed by Firestore Security Rules, so the extension trigger bypasses rules; enforce tenant isolation at the BigQuery layer (RLS and Authorized Views) and the service account boundary.
- Deletes propagate as DELETE changelog rows or CDC deletes, but BigQuery retains history (changelog plus 2-day CDC window plus time-travel). For PII erasure plan explicit purges of the raw and changelog tables and reduce the time-travel window; a Firestore delete alone does not erase the BigQuery copy.

### Risks

- [HIGH] PRD assumes a free or sandbox cost path that is technically impossible (sandbox blocks streaming; extensions need Blaze), causing budget and go-live surprises. — *Mitigation:* Rewrite the cost section around Blaze plus billing-enabled BigQuery; rely on free allowances not sandbox; add budget alerts and a billing-disable safeguard function.
- [HIGH] The sub-5-second SLA is unsupportable, and at-least-once unordered Eventarc delivery can produce duplicate or out-of-order rows that corrupt analytics such as leaderboard and referral counts if treated as exactly-once. — *Mitigation:* Restate as best-effort latency; de-duplicate in the latest view or use BigQuery CDC with _CHANGE_SEQUENCE_NUMBER; make downstream consumers idempotent.
- [MED] Choosing the Firebase extension conflicts with the PRD avoid-firebase-admin and raw Cloud Run plus VPC-SC posture, since the extension is a Firebase-managed Cloud Function. — *Mitigation:* Decide explicitly: accept the extension (fastest, aligns with the sibling app) or build app-level dual-writes via the Storage Write API to honor the VPC-SC and no-firebase-admin stance; document the trade-off.
- [MED] VPC Service Controls could block the extension Cloud Function from reaching the BigQuery API, silently breaking ingestion. — *Mitigation:* If VPC-SC is enforced, add BigQuery and the extension service account to perimeter ingress and egress rules and test end-to-end, or move ingestion to an in-perimeter Storage Write API writer.
- [MED] Storing tenantId and PII only inside the JSON data column prevents BigQuery RLS (cannot apply to JSON) and complicates PII purges. — *Mitigation:* Promote tenantId and any access-control or erasure fields to typed top-level columns via schema views; apply RLS and Authorized Views on those columns.
- [LOW] BigQuery CDC limitations (no mutating DML, no wildcard-table queries, no search indexes; primary key required, max 16 primary-key columns and 2000 columns) may conflict with planned analytics. — *Mitigation:* If adopting CDC for the latest table, keep a separate append-only changelog table for ad-hoc and DML analytics and confirm dashboards do not rely on wildcard tables or search indexes.

### Open questions

- Exact changelog schema columns and IMPORT semantics of the current firestore-bigquery-export version were not in the available corpus; confirm against the extensions.dev README before finalizing BigQuery views.
- Will VPC Service Controls be enforced? If yes, the Firebase-managed extension Cloud Function and BigQuery access must be explicitly allowed in the perimeter, or ingestion moved to an in-perimeter Storage Write API writer.
- Will the team accept the Firebase extension (managed, aligns with the sibling firebase-admin and App Hosting stack) or insist on app-level dual-writes via the Storage Write API to satisfy the avoid-firebase-admin and raw-Cloud-Run direction? This drives the whole pipeline design.
- What is the expected write and event volume per tenant? This determines whether streaming ingestion and Cloud Functions invocations stay within free allowances and whether CDC compute (on-demand versus reservation) is needed.
- Does the dashboard need a guaranteed freshness target? If so, document it as a product target with monitoring (INFORMATION_SCHEMA.WRITE_API_TIMELINE or STREAMING_TIMELINE), since Google provides no SLA for this path.
- What is the PII retention and erasure policy for the BigQuery copy? A Firestore delete does not erase BigQuery history (changelog plus time-travel plus CDC delete window), so an explicit purge process and reduced time-travel window are needed.

## Public ingress + private tenant perimeter network architecture

**Summary:** The PRD's core topology is sound but described with a stale building block: the recommended way to connect Cloud Run to a VPC in 2026 is Direct VPC egress (GA), not a Serverless VPC Access connector. Direct VPC egress scales to zero, has no always-on connector VM charges, and gives lower latency / higher throughput, so the PRD's "Serverless VPC Access connector" should be updated. The public-edge -> internal-processor -> Firestore pattern works: put the public Landing Page Router on internal-and-cloud-load-balancing behind a global external Application Load Balancer with Cloud Armor + Cloud CDN, and set the internal Waitlist Processors / ADK agents to ingress=internal. Firestore is fully VPC-SC supportable (firestore.googleapis.com, which bundles datastore + keyvisualizer) and Cloud Run reaches it via the restricted.googleapis.com VIP (199.36.153.4/30) with all-traffic egress. The big gotcha the PRD misses: VPC-SC enforcement is disabled if a Cloud Run service has ingress=all, so the *public* router cannot itself be a fully-VPC-SC-restricted service the way internal services are -- the perimeter protects Firestore + the internal services, while the public router is protected by the LB/Cloud Armor edge, not by VPC-SC ingress rules. Cloud Armor in 2026 ships OWASP CRS 4.22 preconfigured WAF rules (the PRD/reference-architecture mention of CRS 3.3 is outdated), rate-based bans, and inline reCAPTCHA Enterprise WAF action-token validation. Cloud CDN max TTL constraints make the "1-5 min" counter cache fine. The key tension for the MVP: Firebase App Hosting (the sibling app's stack) provisions its own Google-managed LB + Cloud CDN but does NOT expose a configurable Cloud Armor security policy or VPC-SC ingress controls, so a full Cloud-Armor/VPC-SC perimeter requires raw Cloud Run behind your own LB -- App Hosting cannot be the front door if Cloud Armor/WAF is a hard requirement.

### Validated PRD claims

- **[PARTIALLY-CORRECT]** Public Cloud Run edge router -> Serverless VPC Access connector -> internal Cloud Run + Firestore behind VPC Service Controls is the right topology.
  - Reality: The topology shape is correct and supported, but 'Serverless VPC Access connector' is the outdated mechanism. Google now explicitly recommends Direct VPC egress for Cloud Run -> VPC: it needs no connector VM, scales to zero with the service, charges only for network egress (same egress rate as connectors, no compute/VM charge), and offers lower latency + higher throughput. VPC-SC compliance requires services use Direct VPC egress OR a connector AND route all egress through the VPC (all-traffic) AND set ingress to internal. One real caveat for Direct VPC egress: connection-establishment delays of a minute+ on instance startup (mitigate with an HTTP startup probe), and with Cloud NAT cold-start delays of 30s+, in which case connectors are still recommended. Cloud Run caps throughput at ~1 Gbps per instance.
  - Cites: https://docs.cloud.google.com/run/docs/configuring/connecting-vpc, https://docs.cloud.google.com/run/docs/configuring/vpc-direct-vpc, https://docs.cloud.google.com/run/docs/securing/using-vpc-service-controls
- **[CONFIRMED]** Internal Cloud Run 'Waitlist Processors' / 'ADK agents' should be internal-only (not reachable from the internet); the public router reaches them through the perimeter.
  - Reality: Cloud Run supports three ingress settings: 'internal' (most restrictive; only internal ALB, same-project VPC, and resources allowed by a VPC-SC perimeter that contains the service), 'internal-and-cloud-load-balancing' (internal sources plus external ALB only -- direct run.app hits from the internet are blocked), and 'all'. Set internal services to ingress=internal; set the public router to internal-and-cloud-load-balancing so only LB/Cloud-Armor-filtered traffic reaches it. Enforce org-wide via the run.allowedIngress org policy ('internal' or 'internal-and-cloud-load-balancing') and run.allowedVPCEgress=all-traffic. Also disable the default run.app URL on the public router so users cannot bypass Cloud Armor by hitting run.app directly.
  - Cites: https://docs.cloud.google.com/run/docs/securing/ingress, https://docs.cloud.google.com/run/docs/securing/using-vpc-service-controls, https://docs.cloud.google.com/armor/docs/integrating-cloud-armor
- **[CONFIRMED]** Firestore can sit behind VPC Service Controls and still be reached by Cloud Run.
  - Reality: Firestore is a VPC-SC-supported service. Restricting firestore.googleapis.com in a perimeter also bundles datastore.googleapis.com and firestorekeyvisualizer.googleapis.com. Cloud Run inside the perimeter reaches it over the restricted VIP range restricted.googleapis.com (199.36.153.4/30, TCP 443) via Private Google Access + a Cloud DNS response policy that rewrites *.googleapis.com and *.run.app to that range, plus deny-all-egress firewall rule (priority after 1000) with an allow rule to 199.36.153.4/30. Firestore import/export needs the Firestore service agent (not the default App Engine SA) for full egress protection. No code changes needed for normal reads/writes.
  - Cites: https://docs.cloud.google.com/firestore/native/docs/securing-with-vpc-sc, https://firebase.google.com/docs/firestore/enterprise/securing-with-vpc-sc, https://docs.cloud.google.com/run/docs/securing/using-vpc-service-controls
- **[INCORRECT]** A PUBLIC-ingress Cloud Run service can live fully inside the VPC-SC perimeter.
  - Reality: Setting a Cloud Run service's ingress to 'all' DISABLES VPC Service Controls enforcement for that service -- so a truly public-ingress service is not itself VPC-SC-protected. The supported pattern is: the public Landing Page Router uses ingress=internal-and-cloud-load-balancing (public traffic only via the external ALB, edge-protected by Cloud Armor), while VPC-SC protects Firestore and the internal-only processor/agent services. Additional VPC-SC caveats relevant here: VPC-SC ingress policy enforcement does NOT use the caller's IAM identity for Cloud Run invocations -- only the ANY_IDENTITY identity type and no IAM-principal-based access levels are supported; and continuous deployment (Cloud Build triggers) is unavailable for projects inside a perimeter. So the perimeter protects the data tier, not the public front door.
  - Cites: https://docs.cloud.google.com/run/docs/securing/using-vpc-service-controls, https://docs.cloud.google.com/run/docs/securing/ingress
- **[PARTIALLY-CORRECT]** Global external Application LB + Cloud Armor (WAF, rate-based bans, preconfigured OWASP rules, reCAPTCHA Enterprise WAF action-token) protects the public leaderboard/signup edge.
  - Reality: All capabilities exist and are the right edge design, but version specifics are dated. Cloud Armor preconfigured WAF rules are now sourced from OWASP Core Rule Set 4.22 (rule names like sqli-v422-stable; reference architectures still citing CRS 3.3 are outdated). Sensitivity/paranoia levels 0-4 (default 4); start at sensitivity 1 in preview mode; request-body inspection limited to 64 kB. Rate limiting offers throttle and rate-based-ban actions with enforce-on-key options (IP, XFF-IP, HTTP-HEADER, HTTP-COOKIE, HTTP-PATH, SNI, REGION-CODE, JA3/JA4, user-ip) and exceed actions (deny-403/404/429/502, redirect-to-recaptcha). reCAPTCHA Enterprise action-tokens/session-tokens are validated INLINE at the edge by Cloud Armor (X-Recaptcha-Token header; scores in X-Recaptcha-Wafdata) with no extra backend call -- ideal for the unauthenticated signup endpoint. To prevent LB bypass you MUST disable the Cloud Run default run.app URL or set internal-and-cloud-load-balancing.
  - Cites: https://docs.cloud.google.com/armor/docs/waf-rules, https://docs.cloud.google.com/armor/docs/rule-tuning, https://docs.cloud.google.com/armor/docs/configure-rate-limiting, https://docs.cloud.google.com/armor/docs/bot-management, https://docs.cloud.google.com/recaptcha/docs/implement-waf-ca, https://docs.cloud.google.com/armor/docs/integrating-cloud-armor
- **[CONFIRMED]** Cloud CDN edge cache 1-5 min TTL for public hit counters / leaderboard.
  - Reality: Cloud CDN is supported on global external ALB backend services fronting Cloud Run serverless NEGs (enable with --enable-cdn). A 1-5 minute TTL is well within limits. Best approach for a near-live counter: cache mode USE_ORIGIN_HEADERS with the origin returning Cache-Control: public,max-age=60..300, or CACHE_ALL_STATIC with a default-ttl override. Client-TTL can clamp the browser max-age. Default/maximum overridable TTLs go up to 1 year (31,622,400s); negative caching is capped at 1800s (30 min). Note: CDN caches GET responses by cache key, so per-tenant counters must include the host/tenant in the cache key (default cache key includes host) and PII-masked leaderboard responses must be safe to share across all anonymous viewers of that tenant. IAP is NOT compatible with Cloud CDN.
  - Cites: https://docs.cloud.google.com/cdn/docs/setting-up-cdn-with-serverless, https://docs.cloud.google.com/cdn/docs/using-ttl-overrides, https://docs.cloud.google.com/cdn/docs/using-negative-caching, https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless
- **[CONFIRMED]** Custom-domain host header -> tenantId is resolved at the edge.
  - Reality: The external ALB URL map matches the request Host header against hostRules (exact or wildcard, e.g. *.example.net, and you can include a port like example.net:8080), each pointing to a path matcher / backend; route rules can additionally match on headers/query params. So one LB + one anycast IP can fan many tenant custom domains to the router backend. CRITICAL caveat from Google: the LB does NOT validate the Host header value and clients can set it arbitrarily -- 'You shouldn't use the hostname field to implement access control.' Therefore host-header -> tenantId is fine for ROUTING, but tenant authorization/isolation must be enforced server-side (Firestore rules, scoped service accounts), never by trusting the host alone. At scale, also weigh per-tenant Google-managed cert limits and that each hostname can reference only one host rule.
  - Cites: https://docs.cloud.google.com/load-balancing/docs/url-map-concepts, https://docs.cloud.google.com/load-balancing/docs/https/setup-global-ext-https-serverless
- **[INCORRECT]** The existing Firebase App Hosting deployment can sit behind the Cloud Armor/VPC-SC perimeter (i.e., reuse the sibling app's stack for the public edge).
  - Reality: Firebase App Hosting builds on Cloud Build, serves on Cloud Run, and fronts requests with a Google-managed Cloud Load Balancer + Cloud CDN that App Hosting provisions and controls. App Hosting does NOT expose a knob to attach your own Cloud Armor security policy / WAF / rate-based bans to that managed LB, nor to set Cloud Run ingress=internal or join a VPC-SC perimeter on the public service. App Hosting also manages its own custom-domain SSL via Certificate Manager and its own multi-shard origin -- you don't own the URL map for host-header routing. CONCLUSION: if Cloud Armor WAF + reCAPTCHA-Enterprise-WAF + VPC-SC are hard requirements for the public edge, you must deploy raw Cloud Run behind your own global external ALB (with serverless NEG), NOT Firebase App Hosting. App Hosting remains fine for an MVP that doesn't yet need edge WAF/perimeter.
  - Cites: https://firebase.google.com/docs/app-hosting/about-app-hosting, https://firebase.google.com/docs/app-hosting, https://firebase.google.com/docs/app-hosting/custom-domain, https://docs.cloud.google.com/armor/docs/integrating-cloud-armor

### Recommendations

- [P0] **Replace 'Serverless VPC Access connector' with Direct VPC egress everywhere in the PRD** — Direct VPC egress is GA and the documented recommendation for Cloud Run -> VPC in 2026: no connector VM to size/pay-for, scales to zero, lower latency, higher throughput, same egress billing rate as connectors. Use it for both the Waitlist Processors and ADK agents. Keep a Serverless VPC Access connector ONLY if you hit the known Direct-VPC-egress cold-start gotchas (1min+ connect delay on startup, or 30s+ with Cloud NAT) -- mitigate with an HTTP startup probe that tests egress before serving.
- [P0] **For the public edge, choose raw Cloud Run behind your own global external ALB -- not Firebase App Hosting -- if Cloud Armor/WAF is required** — App Hosting's managed LB does not let you attach a custom Cloud Armor policy, set ingress=internal, or join a VPC-SC perimeter. To get Cloud Armor WAF (OWASP CRS 4.22), rate-based bans, and inline reCAPTCHA Enterprise WAF on the unauthenticated signup/leaderboard endpoints, deploy the Landing Page Router as raw Cloud Run with a serverless NEG behind a global external Application Load Balancer, ingress=internal-and-cloud-load-balancing, and the default run.app URL disabled so users can't bypass Cloud Armor. Align with the sibling app on the @apphosting adapter only for internal/admin surfaces that don't need the edge WAF.
- [P1] **Scope VPC-SC to the DATA tier (Firestore + internal services), not the public router** — Setting ingress=all disables VPC-SC enforcement, so a public-ingress service can't be a fully restricted perimeter member. ## Multi-tenant data isolation (Firestore + BigQuery)

**Summary:** The PRD's core multi-tenancy claim — "Firestore Security Rules enforce matching tenantId" — is materially wrong for the architecture the PRD itself describes. Firestore Security Rules ONLY apply to client (browser/mobile) SDK access; any access through firebase-admin or the @google-cloud/firestore server SDK BYPASSES rules entirely (confirmed in Google docs). Because the PRD funnels all writes through internal Cloud Run "Waitlist Processors" and ADK agents using scoped service accounts, those calls are unauthenticated to the rules engine and rules provide ZERO tenant isolation for them. Tenant isolation MUST be enforced in application code: every server query and write must filter/stamp tenantId, defense-in-depth with a single Firestore database + tenantId field. For Firestore physical layout, a single (default) database with a tenantId field is the correct MVP choice; database-per-tenant is possible (Firestore now supports multiple databases per project) but capped at 100 per project and is the wrong fit for a viral waitlist with potentially thousands of tenants. On BigQuery, the PRD's parameterized "@run_time_tenant_context WHERE" for Row-Level Security is naive and not how RLS works: BigQuery row access policies bind a fixed filter_expression to an IAM grantee-list (user/group/serviceAccount principals, or SESSION_USER()), NOT to arbitrary runtime query parameters. With a shared analytics service account, every tenant's rows resolve to the same principal, so RLS cannot segment them by a query param. The recommended BigQuery pattern for SaaS at scale is dataset-per-tenant with tenant-scoped service accounts (Google's documented best practice), or tenant clustering + authorized views for a small MVP. Finally, the PRD's "BigQuery sandbox/free tier" plan is broken: the sandbox does NOT support streaming inserts, DML, or the BigQuery Data Transfer Service, and all tables auto-expire after 60 days — so it cannot host the Firestore-to-BigQuery streaming pipeline at all. The "<5s near-real-time streaming SLA" is unverified; the firestore-bigquery-export extension is a Cloud Functions-triggered pipeline with no published latency SLA.

### Validated PRD claims

- **[PARTIALLY-CORRECT]** Firestore Security Rules 'enforce matching tenantId' for multi-tenant isolation.
  - Reality: Security Rules ONLY govern client SDK (browser/mobile) access. Per Firebase docs, 'The Firebase Admin SDKs and Cloud Functions can still access your database' and the Admin SDK 'bypasses Firebase Security Rules.' The same applies to the @google-cloud/firestore server SDK. Additionally, 'rules are not filters' — a server-side query is NOT auto-restricted to a tenant; the query itself must carry a where('tenantId','==',X) constraint that matches the rule, or the read is rejected (for client SDK) / unrestricted (for server SDK). Since this PRD routes all writes/reads through Cloud Run service accounts (NOT client SDK), Security Rules contribute nothing to tenant isolation on that path. Isolation must be in application code.
  - Cites: https://firebase.google.com/docs/firestore/security/insecure-rules, https://firebase.google.com/docs/firestore/security/rules-conditions, https://firebase.google.com/docs/firestore/security/rules-query, https://firebase.google.com/learn/quizzes/firebase-security-layers/combine-layers-of-firebase-security-to-protect-your-app
- **[INCORRECT]** PRD says 'avoid firebase-admin; microservices/agents use scoped Google Service Accounts' AND 'Firestore Security Rules enforce matching tenantId.' These two statements are mutually exclusive.
  - Reality: This is an internal contradiction. If you avoid firebase-admin and use scoped service accounts via the @google-cloud/firestore server SDK from Cloud Run, ALL access bypasses Security Rules — so rules enforce nothing. You cannot rely on rules for tenant isolation while also funneling all traffic through server SDKs. Resolution: enforce tenantId in application code on every query/write (mandatory), keep restrictive 'allow read, write: if false' rules as a backstop for any accidental direct client access, and use per-tenant scoped service accounts at the IAM layer.
  - Cites: https://firebase.google.com/docs/firestore/security/insecure-rules, https://firebase.google.com/docs/rules/insecure-rules
- **[INCORRECT]** BigQuery Row-Level Security with a '@run_time_tenant_context' parameterized WHERE clause splits data by tenantId.
  - Reality: BigQuery RLS does NOT take a runtime query parameter. A row access policy binds a FIXED filter_expression to a grantee-list of IAM principals (user:, group:, serviceAccount:, domain:, allAuthenticatedUsers, or workforce/workload identity principals), evaluated like a WHERE clause; alternatively the filter can reference SESSION_USER() to match the querying identity's email. There is no mechanism to inject an arbitrary @tenant_id param into a policy at query time. With a single shared analytics service account, every tenant resolves to the same principal, so RLS cannot separate them. To use RLS for tenancy you would need either (a) one policy per tenant granted to a per-tenant service account, or (b) a SESSION_USER()/lookup-table policy keyed to per-tenant identities — both far heavier than a parameterized WHERE. Google's documented best practice for SaaS multi-tenancy at scale is dataset-per-tenant with tenant-scoped service accounts.
  - Cites: https://docs.cloud.google.com/bigquery/docs/row-level-security-intro, https://docs.cloud.google.com/bigquery/docs/managing-row-level-security, https://docs.cloud.google.com/bigquery/docs/best-practices-for-multi-tenant-workloads-on-bigquery
- **[CONFIRMED]** BigQuery 'Authorized Views split by tenantId' as an isolation option.
  - Reality: Authorized views are a valid, Google-recommended mechanism: a view in a separate dataset is granted access to the source dataset so principals query the view without direct table access. Caveats/limits: a dataset's ACL can hold at most 2,500 authorized resources (views+datasets+functions) — a hard cap that fails at high tenant counts, so Google explicitly recommends grouping views into authorized datasets or moving to dataset-per-tenant/subset-tables when tenants scale. Authorized views must be in the SAME region as the base table and share its partitioning/clustering. Google's multi-tenant guide recommends clustering the base table on tenantId for performance.
  - Cites: https://docs.cloud.google.com/bigquery/docs/authorized-views, https://docs.cloud.google.com/bigquery/docs/authorized-datasets, https://docs.cloud.google.com/bigquery/docs/best-practices-for-multi-tenant-workloads-on-bigquery
- **[INCORRECT]** Use the 'BigQuery sandbox/free tier' (1TB free query/mo) for analytics fed by Firestore streaming.
  - Reality: The BigQuery SANDBOX explicitly does NOT support streaming data (Storage Write API / streaming inserts), DML statements, or the BigQuery Data Transfer Service, and ALL tables/views/partitions auto-expire after 60 days. The Firestore-to-BigQuery streaming pipeline therefore cannot run on the sandbox. The 1TB-queries/10GB-storage FREE TIER (which requires a billing account) is real and persists, but it is a query/storage allowance, not the sandbox, and streaming inserts are billed ($0.01/200 MiB) outside the free batch path. The PRD conflates 'sandbox' (no billing, no streaming) with 'free tier' (billing enabled, streaming allowed but billed). For a streaming analytics pipeline you need a billing-enabled project on the free tier, not the sandbox.
  - Cites: https://docs.cloud.google.com/bigquery/docs/sandbox, https://cloud.google.com/bigquery, https://cloud.google.com/free
- **[UNVERIFIED]** Firestore-to-BigQuery extension provides a '<5s near-real-time streaming SLA' and mirrors create/enrich/state-mutation/delete events.
  - Reality: The firebase/firestore-bigquery-export extension does stream real-time, incremental document changes (create/update/delete) into a BigQuery changelog table and is the documented integration. However, NO Google doc states a '<5s' or any numeric latency SLA. The extension is implemented as a Cloud Functions trigger (event-driven), so latency depends on Cloud Functions cold starts, BigQuery streaming/Storage Write API ingestion, and retry/backfill behavior. Treat <5s as a design target to be load-tested, not a vendor SLA. Note also event ordering and at-least-once delivery semantics require a dedup/ordering strategy on the BigQuery side.
  - Cites: https://firebase.google.com/docs/firestore/solutions/bigquery, https://docs.cloud.google.com/firestore/native/docs/solutions/bigquery
- **[CONFIRMED]** Firestore supports database-per-tenant (multiple databases per project) for customer data isolation.
  - Reality: True — Firestore supports multiple databases per project, and Google lists 'isolate customer data' as an explicit use case. But the hard limit is 100 databases per project (raisable only via support), database IDs can't be reused for 5 minutes after delete, and Cloud Functions v1 triggers don't support named databases (must use 2nd-gen triggers). For a viral waitlist platform expecting many tenants, database-per-tenant does NOT scale and is the wrong MVP choice. Use a single (default) database with a tenantId field instead. Reserve database-per-tenant for a small number of high-value enterprise tenants needing physical/regional isolation or independent CMEK.
  - Cites: https://firebase.google.com/docs/firestore/manage-databases, https://docs.cloud.google.com/firestore/native/docs/manage-databases
- **[CONFIRMED]** Firebase custom claims can carry tenantId/role for RBAC (Normal vs Admin).
  - Reality: Confirmed and appropriate. Custom claims (set via Admin SDK setCustomUserClaims) are delivered in the ID token and readable in Security Rules as request.auth.token.<claim> and verifiable server-side via verifyIdToken. Constraints: claims payload must be <1000 bytes; claims are for access control ONLY (do not store profile data there); they propagate only on next token refresh/sign-in (not instant); and 'custom claims should not be sent directly to the backend' — the backend must verify the ID token, never trust a client-supplied claim. For true per-tenant user pools (separate IdPs, isolated user silos, per-tenant quota/IAM), Identity Platform (GCIP) multi-tenancy is the stronger option; tenant-scoped tokens are only valid for that tenant, preventing token leakage across tenants.
  - Cites: https://firebase.google.com/docs/auth/admin/custom-claims, https://docs.cloud.google.com/identity-platform/docs/multi-tenancy
- **[CONFIRMED]** Leaderboard rank via aggregation count query; 'Firestore charges 1 read per 1000 docs counted.'
  - Reality: Confirmed: count()/sum()/avg() aggregation queries are charged one document read per batch of up to 1,000 index entries matched (minimum one read; e.g., 1,500 entries = 2 reads). IMPORTANT caveats for the leaderboard: (1) aggregation queries are server-only — NOT available with real-time listeners or offline cache; (2) they have a 60-second deadline and scale with the number of index entries SCANNED, not the result size — for a large/hot leaderboard 'count docs where score > userScore' this can be slow and risks DEADLINE_EXCEEDED; (3) the per-1000 read-cost batching means cost grows with rank depth. For the <150ms target at scale, Google recommends distributed counters / precomputed rank buckets rather than a live count-greater-than scan per request.
  - Cites: https://firebase.google.com/docs/firestore/pricing, https://firebase.google.com/docs/firestore/query-data/aggregation-queries
- **[CONFIRMED]** Tenant-scoped queries need composite indexes.
  - Reality: Confirmed. Any tenant-scoped query that combines the equality filter where('tenantId','==',X) with an orderBy or a range/inequality on another field (e.g., score for the leaderboard, createdAt for recent signups) requires a composite index on (tenantId ASC, <secondField> ASC/DESC). Best practice: order index fields as equalities first, then the most selective range/inequality — so (tenantId, score) for the leaderboard. A descending leaderboard needs a separate (tenantId ASC, score DESC) index. Note the billing nuance: queries with at most ONE range field are NOT charged for index-entry reads; two+ range fields (or a range plus orderBy on a different field, or __name__ used as a range) ARE charged for index entries.
  - Cites: https://firebase.google.com/docs/firestore/query-data/index-overview, https://docs.cloud.google.com/firestore/native/docs/query-data/multiple-range-fields, https://firebase.google.com/docs/firestore/pricing

### Recommendations

- [P0] **Enforce tenant isolation in application code, not Security Rules, on every server query/write** — Because all access flows through Cloud Run service accounts (server SDK), Security Rules are bypassed and provide no isolation. Implement a single shared data-access layer that ALWAYS injects where('tenantId','==',ctx.tenantId) on reads and stamps tenantId on writes, with the tenantId derived server-side from the verified host->tenant mapping or verified ID token claim — never from client-supplied body. Add a Zod-validated tenant context and unit tests (Vitest) asserting no query path can omit the tenantId filter. Keep Firestore rules locked to 'allow read, write: if false' as a backstop against accidental direct client access.
- [P0] **Use a single Firestore (default) database with a tenantId field for the MVP; do NOT do database-per-tenant** — Database-per-tenant is capped at 100 databases/project and adds operational drag (named-DB trigger limits, 5-min ID reuse delay) that does not fit a viral, many-tenant waitlist. Single database + tenantId field is the correct pattern. Reserve multiple-databases only for a handful of enterprise tenants that require regional residency or independent CMEK.
- [P0] **Replace the naive BigQuery '@run_time_tenant_context WHERE / RLS' design** — RLS binds filters to IAM grantees, not query params. Choose one: (a) MVP-simple: a single tenant-clustered table (CLUSTER BY tenantId) exposed via per-tenant AUTHORIZED VIEWS in a separate dataset, granting each tenant's scoped service account access to only its view (watch the 2,500 authorized-resources/dataset cap — group into authorized datasets as you grow); or (b) scale-ready, Google's recommended SaaS pattern: DATASET-PER-TENANT with a tenant-scoped service account per dataset and Dataflow/extension dual-writing into the tenant dataset. If you genuinely want RLS, key it to per-tenant service-account principals or SESSION_USER() lookup tables, not a runtime parameter.
- [P0] **Drop the 'BigQuery sandbox' from the streaming analytics plan** — The sandbox cannot ingest streaming data, run DML, or use the Data Transfer Service, and auto-expires tables at 60 days — fatal for the Firestore-to-BigQuery pipeline. Use a billing-enabled project on the on-demand free tier (1 TiB queries + 10 GiB storage/month). Budget for streaming-insert costs ($0.01 per 200 MiB) since streaming is billed even within free tier, and set explicit table partition/expiration policies rather than relying on sandbox defaults.
- [P1] **Evaluate Identity Platform (GCIP) multi-tenancy vs. plain custom claims** — For a B2B SaaS where each tenant may want its own sign-in/IdP and strict user-silo isolation, GCIP multi-tenancy gives per-tenant user pools, per-tenant IAM/quota, and tenant-scoped tokens that are invalid across tenants (prevents token leakage). If the MVP only needs a tenantId+role tag on a shared user pool, custom claims (<1000 bytes, access-control only, verified server-side via verifyIdToken) are sufficient and cheaper. Decide before building auth, as migration later is costly.
- [P1] **Pre-create composite indexes for tenant-scoped leaderboard/recent queries** — Define (tenantId ASC, score DESC) for the leaderboard and (tenantId ASC, createdAt DESC) for recent signups in firestore.indexes.json, with equalities-before-range ordering. Avoid queries with two range fields where possible (they incur index-entry read charges); keep the leaderboard to a single range field per query.
- [P1] **Re-architect the leaderboard rank computation away from live count-greater-than scans** — The 'count docs where score > userScore' aggregation scales with index entries scanned (not result size), has a 60s deadline, and cannot be used with real-time listeners. For the <150ms target, use distributed/sharded counters or periodically materialized rank buckets, and cache hot counters at the CDN edge (the PRD's 1-5 min edge cache) rather than recomputing rank per request.
- [P2] **Add a dedup/ordering strategy for the Firestore->BigQuery changelog** — The export extension is event-driven (at-least-once, Cloud Functions latency-dependent) with no <5s SLA. Treat <5s as a target to load-test. Build the BigQuery consumer to dedupe on document_id+timestamp and reconstruct latest-state views (the extension provides a latest-state view), so duplicate or out-of-order create/update/delete events don't corrupt per-tenant analytics.

### Security notes

- Critical: server-side Firestore access (firebase-admin OR @google-cloud/firestore) BYPASSES Security Rules. The PRD's reliance on rules for tenantId enforcement is void for the Cloud Run service-account path. Application-code filtering is the actual control plane.
- 'Rules are not filters': even on the client path, a query without an explicit where('tenantId','==',X) constraint matching the rule is REJECTED, not silently scoped. Server SDK queries without that filter return cross-tenant data with no error — a silent isolation breach.
- Custom claims must never be trusted from the client; the backend must verify the ID token (verifyIdToken) and read claims from the verified token. Claims propagate only on token refresh, so revocation/role changes are not instant.
- BigQuery RLS row access policies log creation/deletion to Cloud Audit Logs but the filter_expression and grantee_list are omitted from logs (may contain sensitive data). Reads against RLS tables surface the policy in IAM authorization info — enable audit logging/monitoring for cross-tenant access detection.
- RLS is vulnerable to query-duration side-channel attacks at shard boundaries; for the strongest isolation of tenant data where row counts must be secret, Google recommends SEPARATE TABLES/datasets over RLS or authorized views.
- A shared analytics service account querying a multi-tenant BigQuery table defeats RLS (all tenants = one principal). Use per-tenant scoped service accounts or dataset-per-tenant to make the IAM identity the isolation boundary.
- Tenant context must be derived server-side from the verified host->tenantId mapping at the edge or a verified token claim, never from a client-supplied tenantId in the request body, or tenants can spoof into each other's data.
- GCIP tenant-scoped tokens are valid only within their tenant, preventing the token-leakage/cross-tenant-replay risk that exists with project-level Firebase Auth tokens carrying a tenantId claim.

- [HIGH] Cross-tenant data leak: code path forgets to add where('tenantId','==',X); server SDK returns all tenants' data with no rules backstop and no error. — *Mitigation:* Centralize ALL Firestore access behind a single tenant-aware repository that injects tenantId; forbid raw db.collection() calls via lint rule; add Vitest tests asserting every query carries a tenant filter; code-review gate.
- [HIGH] BigQuery RLS designed around a runtime parameter never actually isolates tenants because policies bind to IAM principals, not params — shipped 'isolation' is illusory. — *Mitigation:* Adopt dataset-per-tenant + per-tenant scoped service accounts (Google best practice) or per-tenant authorized views; if using RLS, key it to per-tenant service-account principals; validate with a red-team query as a wrong-tenant identity.
- [HIGH] Streaming analytics pipeline silently fails or is impossible on the BigQuery sandbox (no streaming/DML/DTS; 60-day table expiry). — *Mitigation:* Use a billing-enabled project on the free tier; explicitly configure partitioning and table expiration; remove all 'sandbox' assumptions from the PRD and infra-as-code.
- [MED] Leaderboard live count-greater-than aggregation exceeds the 60s deadline or blows the <150ms target as the waitlist grows hot, and can't be used with real-time listeners. — *Mitigation:* Use sharded distributed counters / materialized rank buckets; serve cached counters via CDN edge cache; reserve aggregation count() for low-frequency admin reporting.
- [MED] Authorized-view-per-tenant design hits the 2,500 authorized-resources-per-dataset hard cap as tenant count grows. — *Mitigation:* Group views into authorized datasets, or move to dataset-per-tenant/subset-tables before approaching the cap; cluster base tables on tenantId.
- [MED] Per-tenant service accounts exhaust the 100 service-accounts-per-project soft quota at scale. — *Mitigation:* Request quota increase early, or group multiple tenants per service account / per reservation project as Google's SaaS guidance describes.
- [MED] At-least-once, latency-variable Firestore->BigQuery delivery produces duplicate or out-of-order events, corrupting per-tenant counts. — *Mitigation:* Dedupe on document_id+timestamp; consume the extension's latest-state view; reconcile periodically against Firestore source of truth.
- [LOW] Custom-claim staleness: a demoted admin or moved tenant retains old access until token refresh. — *Mitigation:* Force token refresh on role change (metadata refreshTime pattern); keep token lifetimes short; re-verify critical authz server-side per request.

### Open questions

- How many tenants and what tenant-growth rate is expected? This determines single-DB+tenantId vs dataset-per-tenant vs authorized-views and whether the 100-database / 2,500-authorized-resource / 100-service-account limits bite.

- Is the team willing to maintain a strict centralized data-access layer (the only reliable tenant-isolation control given server-SDK rule bypass), or does it expect rules to carry that weight (they cannot)?

## OWASP-aligned security posture for a multi-tenant SaaS waitlist platform with public unauthenticated endpoints (vizzybl-marketing)

**Summary:** The PRD's defense-in-depth direction is sound and maps cleanly onto OWASP Top 10 2021, OWASP API Security Top 10 2023, and OWASP LLM Top 10: the highest-risk items for this design are API1:2023 Broken Object Level Authorization (tenant isolation across public/agent paths), API2/A07 broken auth on the public endpoints, A03 injection, A10/SSRF from agents, A05 security misconfiguration of the public surface, and LLM01 prompt injection. Most named GCP controls are real and current as of mid-2026: reCAPTCHA Enterprise score-based keys plus WAF action/session tokens that Cloud Armor decodes at the edge; Cloud Armor preconfigured WAF rules now track OWASP CRS 4.22 (CRS 3.0 should be avoided); rate-based ban rules; Sensitive Data Protection (DLP) for PII masking; Secret Manager (AES-256, IAM-scoped, CMEK-capable); Cloud Audit Logs (Admin Activity always-on, Data Access opt-in); Firestore Security Rules and BigQuery row-level security / authorized views for tenant splitting; per-service service accounts for least privilege; and Model Armor for prompt-injection/jailbreak and output scanning. Two PRD claims are stale or imprecise: 'ADK 2.0' is unverified as a version string (the sibling app pins @google/adk ^0.3.0), and the product the PRD calls 'Gemini Enterprise Agent Platform Agent Identity' is real but the current GA identity primitive is SPIFFE-based Agent Identity with some sub-features still in Preview. The single most load-bearing secure-default to bake in now: server-side tenant authorization on every path (no client-trusted tenantId) and server-side PII masking before serialization, because Firestore client SDK reads are governed only by Security Rules and a public leaderboard cannot rely on them.

### Validated PRD claims

- **[CONFIRMED]** Use reCAPTCHA Enterprise at the edge for the public signup and leaderboard endpoints (score-based + WAF action tokens), integrated with Cloud Armor.
  - Reality: reCAPTCHA Enterprise supports SCORE integration keys and WAF keys (action-token, session-token, challenge-page) whose wafService is 'CA' (Cloud Armor). Cloud Armor decodes/validates the token at the edge instead of the backend and exposes scores via the X-Recaptcha-Wafdata header (e.g. action_token;score=0.9). Scores are 0.0 (high risk/fraud) to 1.0 (legitimate) across 11 levels, but only 4 levels (0.1/0.3/0.7/0.9) and reason codes are available until a billing account is added. Backends must call projects.assessments.create server-side (never client-side), verify tokenProperties.valid and that action==expectedAction (mismatch = forged action), and tokens are single-use and expire after 2 minutes. ## Leaderboard / viral scoring engine — correctness & cost on Firestore

**Summary:** The PRD's Firestore-native leaderboard design is mostly sound and its headline pricing claim is essentially correct: Firestore bills aggregation queries (count/sum/avg) at 1 read per batch of up to 1000 index entries scanned, with a minimum of 1 document read when 0 entries are scanned. The rank-by-count pattern (count where tenantId==X && campaignId==Y && isVerified==true && score > userScore, then +1) is valid and requires a composite index (equality fields first: tenantId, campaignId, isVerified; then the range field score). A crucial nuance the PRD misses: a query with up to ONE range field (score here) is EXEMPT from index-entry read charges entirely — so the rank count() is billed as just 1 document read regardless of how many docs it counts, which is even cheaper than the PRD assumes. However, count() scales with dataset size (not result size) and has a 60s DEADLINE_EXCEEDED ceiling, so a per-request rank scan over a viral campaign with millions of signups will blow the <150ms target; the rank MUST be served from a cache or precomputed counter, not computed live per request. The score formula Score = Referrals*500 - signupUnixTimestamp tie-breaks in the correct DIRECTION (earlier signup ranks higher when sorted DESC) but has two real defects: (1) a seconds-vs-milliseconds magnitude trap — Firestore integers are 64-bit and JS numbers are IEEE-754 doubles safe only to 2^53, and if ms are ever mixed with seconds the timestamp term swamps referrals entirely; (2) even in seconds, one referral is only worth 500 seconds (8.3 min) of signup priority, so the referral incentive is far weaker than likely intended. Hot-document write contention on a popular referrer doc is a genuine viral-load risk (Firestore cannot split below a single document; sustained high write rates to one doc cause contention/latency), and FieldValue.increment plus distributed/sharded counters are the documented mitigations. Caching the public leaderboard via Cloud CDN (s-maxage/max-age with Cache-Control: public) is the right way to hit <150ms and avoid per-request scans; edge cases (empty -> [], invalid waitlist id -> 404) are application concerns the PRD must specify, and referral idempotency/self-referral must be enforced with a transaction or a uniqueness doc, not a bare increment.

### Validated PRD claims

- **[CONFIRMED]** Firestore aggregation count() is billed at '1 read per 1000 index entries scanned' (min 1).
  - Reality: Firestore charges one read operation for each batch of up to 1000 index entries read by a query. For aggregation queries (count/sum/avg) that read 0 index entries, there is a minimum charge of one document read; count() reading 0-1000 entries = 1 read, reading 1500 entries = 2 reads. Aggregation pricing scales with index entries MATCHED, not documents returned.
  - Cites: https://firebase.google.com/docs/firestore/pricing, https://firebase.google.com/docs/firestore/query-data/aggregation-queries, https://firebase.google.com/docs/firestore/billing-example
- **[PARTIALLY-CORRECT]** Rank = count(where tenantId==X && campaignId==Y && isVerified==true && score > userScore) + 1, served natively from Firestore.
  - Reality: The pattern is valid Firestore. It requires a COMPOSITE INDEX ordered equality-fields-first then the range field: (tenantId ASC, campaignId ASC, isVerified ASC, score ASC). Firestore uses leftmost index fields for equality constraints then the range/inequality on score. IMPORTANT cost nuance the PRD omits: queries with UP TO ONE range field are EXEMPT from index-entry read charges, so this count() is billed as just 1 document read regardless of how many entries it counts (the equality filters + single range on score = exactly one range field). But count() scales with DATASET size and hits DEADLINE_EXCEEDED at 60s; for million-row viral campaigns a live per-request rank scan is too slow for the <150ms target and must be cached or replaced by a precomputed counter.
  - Cites: https://firebase.google.com/docs/firestore/pricing, https://firebase.google.com/docs/firestore/query-data/aggregation-queries, https://firebase.google.com/docs/firestore/query-data/multiple-range-fields
- **[PARTIALLY-CORRECT]** Score = Referrals*500 - signupUnixTimestamp, stored and sorted natively in Firestore; earlier signup ranks higher at equal referrals.
  - Reality: Tie-break DIRECTION is correct: with the same referral count, the earlier (smaller) timestamp yields a larger score, so sorting score DESC ranks earlier signups higher. But there are two defects. (1) Magnitude/precision trap: Firestore Integer is 64-bit signed and Floating-point is 64-bit IEEE-754 double; JS clients (the sibling stack is Next.js/TS) represent all numbers as doubles, safe only to MAX_SAFE_INTEGER 2^53 = 9,007,199,254,740,992. Unix SECONDS in 2026 is ~1.78e9 (10 digits, safe). Unix MILLISECONDS is ~1.78e12 (13 digits, still < 2^53 so no overflow) — BUT if ms are ever used or mixed with seconds, the timestamp term (1.78e12) dwarfs Referrals*500 so referrals become numerically irrelevant. The PRD must pin the unit (seconds) explicitly and never use Date.now() (ms) for this field. (2) Weighting: in seconds, one referral = 500 score points = only 500 seconds (8.3 minutes) of signup priority, so a 0-referral user who signed up >8.3 min earlier outranks a brand-new 1-referral user. That is likely far weaker referral weighting than intended. Also all scores are large negatives near -1.78e9, which is non-intuitive and brittle.
  - Cites: https://firebase.google.com/docs/firestore/manage-data/data-types, https://docs.cloud.google.com/firestore/native/docs/concepts/data-types, https://firebase.google.com/docs/firestore/query-data/order-limit-data
- **[PARTIALLY-CORRECT]** Referral counters / score updates on a single referrer document under viral load.
  - Reality: Firestore cannot split a key range below a single document, so sustained high concurrent writes to one referrer doc cause contention, higher latency, and errors (hotspotting). The documented guidance: ramp via the 500/50/5 rule (start at 500 ops/s, +50% every 5 min); use FieldValue.increment for atomic counter updates; and for write rates beyond what one doc handles, use DISTRIBUTED (sharded) counters — value = sum of N shard docs, throughput scales ~linearly with shard count. A monotonically increasing indexed field (like score or a timestamp) on a high-write collection caps at ~500 writes/s unless the field is index-exempted. The PRD should plan sharded counters for top referrers and consider index exemptions on hot sequential fields.
  - Cites: https://firebase.google.com/docs/firestore/solutions/counters, https://firebase.google.com/docs/firestore/best-practices, https://firebase.google.com/docs/firestore/understand-reads-writes-scale
- **[CONFIRMED]** Cache the public leaderboard at the edge (Cloud CDN / response cache 1-5 min) to hit <150ms and avoid per-request Firestore scans.
  - Reality: Cloud CDN caches GET responses that carry a Cache-Control header with max-age or s-maxage (s-maxage takes precedence; use Cache-Control: public, s-maxage=60..300). A public unauthenticated leaderboard is ideal for this. Caveats: responses with Set-Cookie or Cache-Control: private/no-store are NOT cached, and requests carrying an Authorization header are only cached under specific directives — so the leaderboard endpoint must be strictly anonymous and cookie-free at the edge. With CACHE_ALL_STATIC/USE_ORIGIN_HEADERS modes the origin headers drive freshness; serve-while-stale can hide origin latency on revalidation. This is the correct mechanism to keep p95 well under 150ms and eliminate per-request count()/scan load.
  - Cites: https://docs.cloud.google.com/cdn/docs/caching, https://docs.cloud.google.com/cdn/docs/using-cache-modes
- **[UNVERIFIED]** Idempotent referral attribution (prevent self-referral and double counting).
  - Reality: Firestore provides the primitives but the PRD does not specify the mechanism. A bare FieldValue.increment is NOT idempotent — a retried/duplicate request double-counts. The documented safe pattern is a TRANSACTION (reads-before-writes; auto-retried on contention) or a uniqueness guard: write a referral-edge doc keyed by (referrerId+refereeId) with create-only semantics (security rule: allow create only if !exists), and increment inside the same transaction so the count only moves when the edge is newly created. Self-referral is prevented by rejecting referrerId == refereeId. This must be specified explicitly; it is currently a gap.
  - Cites: https://firebase.google.com/docs/firestore/manage-data/transactions

### Recommendations

- [P0] **Do not compute rank live per request; precompute or cache it** — A live count(score > userScore) over a viral campaign scans the whole matching dataset and is subject to the 60s DEADLINE_EXCEEDED ceiling and unbounded latency — it cannot meet <150ms at million-row scale. Serve the top-N leaderboard from Cloud CDN (Cache-Control: public, s-maxage=60..300) and serve a user's own rank either from a short-TTL cache or from a periodically-recomputed bucketed/rollup counter. The count() pattern is fine for an admin/occasional recompute, not the public hot path.
- [P0] **Pin the timestamp unit to SECONDS and store score as a 64-bit integer; fix referral weighting** — Specify in the PRD that signupUnixTimestamp is in seconds (10 digits), never milliseconds (Date.now()). Store score as an integer. Document that JS doubles are safe only to 2^53, so never mix ms and s. Reconsider the 500 weight: one referral currently equals only 8.3 minutes of signup priority, which makes referrals weak relative to early signup. Pick a weight that reflects intended virality (e.g., referrals dominate, time only breaks exact ties) — e.g. Score = Referrals*1e9 - signupSeconds, or sort primarily by referrals DESC then signupTimestamp ASC via a composite index, which avoids the magic-number fragility entirely.
- [P1] **Create the explicit composite index and exploit the single-range cost exemption** — Define composite index (tenantId ASC, campaignId ASC, isVerified ASC, score DESC) for both the top-N leaderboard query and the rank count(). Because the query has exactly one range field (score), it is exempt from index-entry read charges — the rank count() bills as 1 document read no matter how many docs it counts. Keep it to one range field; adding a second inequality (e.g. a date range) would reintroduce per-1000-entry charges.
- [P1] **Use sharded distributed counters for hot referrers and atomic increments** — Top referrers under viral load will exceed single-document write limits. Use FieldValue.increment for atomic updates and distributed counters (subcollection of shards, value = sum of shards) for the hottest docs; throughput scales ~linearly with shard count. Follow the 500/50/5 ramp rule for new campaigns. Consider index exemptions on monotonically increasing hot fields to bypass the ~500 writes/s sequential-field cap.
- [P1] **Make referral attribution idempotent and reject self-referral in a transaction** — Replace any bare increment with a transaction that creates a unique referral-edge doc keyed (referrerId, refereeId) create-only and increments the referrer count in the same atomic operation, so retries/duplicates cannot double-count. Reject referrerId == refereeId. Enforce both in security rules and server logic.
- [P2] **Specify leaderboard edge cases explicitly** — Empty leaderboard and length=0 must return [] (not null/404); an unknown/invalid waitlist or campaign id must return 404 distinct from an empty-but-valid campaign returning 200 []. These are application-layer contracts not provided by Firestore and must be in the API spec and tests.

### Cost notes

- Aggregation count(): 1 read per up to 1000 index entries scanned; min 1 read at 0 entries. Read price reference in docs: $0.06 per 100,000 reads (region-dependent). Example from Google docs: counting 10M docs/day = 10,000 reads/day = ~$0.18/month.
- Cost nuance the PRD misses: a query with up to ONE range field is EXEMPT from index-entry read charges. The rank count() (3 equality filters + 1 range on score) therefore bills as 1 document read regardless of count size — materially cheaper than the PRD's '1 read per 1000 counted' assumption. Adding a second inequality field would remove this exemption.
- Firestore free tier: 50,000 document reads/day, 20,000 writes/day, 20,000 deletes/day, 1 GiB stored, 10 GiB/month egress; exactly ONE free database per project. TTL/PITR/backup/restore/clone are NOT in the free tier. This is Firestore-specific and unrelated to the PRD's separate 'BigQuery 1TB free query/mo' claim.
- Distributed counters trade write throughput for read cost: reading the counter total costs N reads (one per shard) because the whole shards subcollection is loaded. Keep a slower-cadence rollup doc if reads dominate.
- Offsets are billed as reads for every skipped document — never use offset() for leaderboard pagination; use cursors (startAfter), which only bill for returned docs.
- Cloud CDN cache hits cost CDN egress/lookup, not Firestore reads — caching the public leaderboard converts per-request Firestore read load into cheap edge cache hits, the dominant cost lever for a viral public endpoint.

### Security notes

- The public leaderboard endpoint must be strictly anonymous and cookie-free: Cloud CDN will NOT cache responses with Set-Cookie or Cache-Control: private/no-store, and only caches Authorization-bearing requests under narrow conditions. A stray session cookie silently disables edge caching and pushes load back onto Firestore.
- PII masking must happen server-side BEFORE the response enters the CDN cache; once a response with un-masked PII is cached at the edge it is served to all anonymous clients. Cache only the masked projection.
- Referral idempotency is a security control, not just correctness: without a create-only uniqueness edge + transaction, attackers can inflate their rank by replaying the referral webhook. Enforce referrerId != refereeId and one-edge-per-pair in both security rules and server code.
- Firestore Security Rules apply identically to aggregation queries as to document queries — clients can run count() only where rules permit the underlying collection query. If the leaderboard is served by a backend service account (not client SDK), rules are bypassed, so tenant isolation (tenantId/campaignId equality filters) must be enforced in server code and cannot rely on rules alone.

### Risks

- [HIGH] Live per-request rank count() over a viral (million-row) campaign exceeds the <150ms target and can hit the 60s DEADLINE_EXCEEDED ceiling; aggregation scales with dataset size, not result size. — *Mitigation:* Serve top-N and rank from Cloud CDN short-TTL cache and/or precomputed rollup counters; reserve live count() for admin recompute, not the public hot path.
- [HIGH] Seconds-vs-milliseconds magnitude bug in Score = Referrals*500 - signupTimestamp: mixing units makes the timestamp term swamp referrals, silently corrupting ranking; JS doubles also constrain safe-integer range to 2^53. — *Mitigation:* Pin unit to seconds, store score as integer, forbid Date.now()/ms, and unit-test the ordering. Prefer a two-field sort (referrals DESC, signup ASC) over a magic-number scalar.
- [HIGH] Hot-document write contention on a popular referrer's counter under viral spikes causes contention errors and latency; Firestore cannot split below a single document. — *Mitigation:* FieldValue.increment + distributed/sharded counters for hot referrers; 500/50/5 ramp; index-exempt hot sequential fields.
- [MED] Non-idempotent referral attribution (bare increment) allows double-counting on retries and rank inflation by replay. — *Mitigation:* Transaction with create-only referral-edge uniqueness doc + same-transaction increment; reject self-referral.
- [MED] Referral weight of 500 (= 8.3 min of signup priority) likely under-incentivizes referrals relative to early signup, undermining the viral mechanic. — *Mitigation:* Re-tune weighting or switch to multi-field ordering so referrals clearly dominate and timestamp only breaks exact ties.
- [MED] A leaked session cookie or Authorization header on the public leaderboard disables CDN caching, collapsing edge protection and exposing Firestore to full unauthenticated request volume. — *Mitigation:* Strict anonymous, cookie-free leaderboard endpoint; verify Cache-Control: public, s-maxage on responses; load-test cache hit ratio.

### Open questions

- What is the expected unit for signupUnixTimestamp (seconds vs ms), and is score stored as Firestore Integer or as a JS double on the client write path? This determines whether the magnitude bug is latent.
- What peak write rate is expected on the single hottest referrer document during a viral spike? This sets the required shard count for distributed counters.
- Is the per-user 'your rank' value required in real time, or is a 1-5 min stale rank acceptable? Acceptable staleness lets the rank be served from cache/rollups and removes the live count() from the hot path.
- Is the public leaderboard served via the client Firestore SDK (rules-enforced) or a backend service account (rules bypassed)? This changes where tenantId/campaignId isolation must be enforced.
- Does the design need ties broken deterministically beyond timestamp (e.g., two users with identical referrals AND identical signup second)? If so a final __name__ tiebreak is needed, which would add a second range field and reintroduce index-entry read charges on the rank query.
- Will the leaderboard ever need a second inequality (e.g., date-windowed 'this week' rankings)? That would remove the single-range cost exemption and require re-costing.

## Hosting/runtime & framework fit for the Waitlist MVP

**Summary:** Firebase App Hosting is the correct primary runtime for the vizzybl-marketing MVP and aligns with the sibling vizzybl-portal convention. App Hosting is not an alternative to Cloud Run; it IS managed Cloud Run plus Cloud CDN plus Cloud Build plus Cloud Secret Manager plus a Google-managed Cloud Load Balancer, with zero-config Next.js 15 detection, scale-to-zero (minInstances 0 default), and zero idle cost on the Blaze free tier. The PRD framing of avoid firebase-admin and deploy on raw Cloud Run with VPC-SC is largely a false dichotomy for the public landing page and admin portal, and several pieces (internal-only Cloud Run, VPC-SC perimeter, Agent Engine) are over-engineered for an MVP and should be deferred. The one real architectural gap is that App Hosting managed load balancer is NOT customer-configurable, so you cannot attach Cloud Armor or reCAPTCHA Enterprise WAF action-tokens at that edge; reCAPTCHA Enterprise must instead be integrated at the application layer via server-side createAssessment (first 10k assessments per month free). For the latency targets, App Hosting Cloud CDN serves cacheable GETs (hit counters, leaderboard) at the edge, and a small minInstances setting on the SSR backend removes cold starts. Async work (offboarding emails, blast queue) should use Cloud Tasks (at-least-once, idempotent handlers, up to 30-min timeout) and Firestore to Eventarc for state-change fan-out. The smallest secure footprint is one App Hosting backend per environment in a separate GCP/Firebase project (dev plus prod), plus Firestore, reCAPTCHA Enterprise, Identity Platform multi-tenancy, Cloud Tasks, and Secret Manager, deferring the LB plus Cloud Armor plus VPC-SC perimeter and internal-only microservices until traffic or compliance justify them.

### Validated PRD claims

- **[PARTIALLY-CORRECT]** Deploy on raw Cloud Run with VPC Service Controls and AVOID firebase-admin / Firebase App Hosting (the sibling app convention).
  - Reality: This is a false dichotomy for the runtime layer. Firebase App Hosting is itself built on Cloud Run: Apps are built with Cloud Build, served on Cloud Run with automatic scaling, and cached in Cloud CDN; integrated services like Cloud Secret Manager keep API keys safe. For the MVP public landing page plus admin portal plus signup API, App Hosting on Cloud Run is the right, convention-aligned choice; raw Cloud Run should be reserved only for genuinely internal-only services (deferred post-MVP).

- **[CONFIRMED]** Idempotent serverless processing for signup writes; Cloud Tasks / Eventarc for async offboarding emails and blast queue.
  - Reality: Correct and well-aligned with current products. Cloud Tasks provides at-least-once delivery to a private/Cloud Run HTTP target with OIDC auth (OidcToken plus service account), configurable rate limits, retries, scheduled delivery, and dedup; in some rare circumstances multiple task execution is possible, so your handlers should be idempotent. MVP security relies on App Check, application-layer reCAPTCHA, server-side tenant validation, and least-privilege service accounts, not network isolation.
- Firestore Security Rules only protect client-SDK access. Server-side writes via the Admin SDK or service-account credentials bypass rules, so tenantId scoping and PII handling for the signup/leaderboard endpoints must be enforced in route-handler code, with mandatory PII masking applied before any unauthenticated GET response.
- Use a distinct, minimally-scoped Google service account per service (router, worker, agents) rather than a single master key, granting only Cloud Tasks Enqueuer, Datastore User, Secret Manager Accessor, recaptchaenterprise.agent as needed, consistent with the PRD per-agent identity intent.
- If you later add a self-managed LB, set Cloud Run ingress to internal-and-cloud-load-balancing and use org policy run.allowedIngress so the run.app URL cannot bypass the LB/Cloud Armor; ingress=all silently disables VPC-SC enforcement.

### Risks

- [MED] Cold starts on scale-from-zero (pending queue up to 10s or 3.5x startup) cause the public router/leaderboard to miss the sub-150-200ms targets on uncached requests. — *Mitigation:* Set minInstances greater than or equal to 1 in prod apphosting.yaml, enable startup CPU boost, lazy-load heavy deps, and maximize CDN cache-hit rate for counters/leaderboard via s-maxage; keep those routes free of middleware/cookies.
- [MED] PRD assumes edge Cloud Armor plus reCAPTCHA WAF on the platform LB, which App Hosting cannot provide, leaving the public signup endpoint without L7 rate-limiting if implemented as designed. — *Mitigation:* Use application-layer reCAPTCHA Enterprise createAssessment plus App Check plus per-IP/per-tenant rate limiting in the route handler for MVP; add a self-managed LB plus Cloud Armor only post-MVP if abuse appears.
- [HIGH] Over-engineering the MVP with VPC-SC, internal-only Cloud Run, and Agent Engine adds large ops/cost overhead and is incompatible with the App Hosting convention, risking premature complexity (the inverse of the team tech-debt concern). — *Mitigation:* Ship the lean App Hosting plus Firestore plus Cloud Tasks plus Identity Platform footprint first; gate the perimeter/internal-services work behind an explicit compliance or scale trigger documented as a post-MVP milestone.
- [MED] At-least-once delivery (Cloud Tasks, Eventarc) plus unordered Firestore events can duplicate waitlist entries or double-send emails. — *Mitigation:* Deterministic Firestore doc IDs (normalized email / idempotency key) for signup; idempotent, side-effect-safe email/blast handlers; dedup keys on tasks.
- [MED] Unauthenticated public endpoints on a billing-enabled (Blaze) project mean bandwidth/abuse can drive unbounded spend; budget alerts do not cap charges. — *Mitigation:* Set budget alerts plus a programmatic billing-disable function; cap maxInstances; aggressively cache; enforce reCAPTCHA plus App Check; consider disposable-email filtering before write.

### Open questions

- Does the team require a true VPC-SC data-exfiltration perimeter for any compliance reason (e.g., enterprise customers)? If yes, the public router must be raw Cloud Run behind a self-managed LB rather than App Hosting, changing the MVP footprint.
- Will the admin portal and public landing page share one App Hosting backend/repo or be split into two backends (different scaling/security)? Affects custom-domain and minInstances strategy.
- Which email provider/SDK is the agentic email hub using, and does its send latency fit within Cloud Tasks 30-min handler limit per batch, or does the blast need chunking/Cloud Run jobs?
- Is tenantId resolved purely by custom-domain host header, or also by path/subdomain? This determines the App Hosting custom-domain configuration and the server-side mapping table design.
- What Next.js rendering mode is each public route (static/ISR/SSR)? Determines CDN cacheability and whether minInstances is even needed for the latency target.
- Confirm the target App Hosting region(s) for dev/prod; Cloud CDN edge caching helps globally, but the Cloud Run origin region affects cold-path latency and Firestore co-location.
